# Auftrag 4.3: Zwei VMs im VNet, Verbindungen testen

Zeit: 60 Min. · Form: Partnerarbeit (jede Person in ihrem eigenen Abonnement (Subscription))

## Ziel
- Du kannst eine VM in ein bestimmtes Subnetz (Subnet) stellen, mit und ohne öffentliche IP (Public IP). (K3)
- Du kannst eine NSG mit einem Subnetz (Subnet) verknüpfen. (K3)
- Du kannst die Verbindung zwischen zwei VMs mit `ping` und `ssh` testen. (K3)

## Voraussetzungen
- Auftrag 4.2 erledigt, `vnet-tag4-<kuerzel>` mit `snet-web` und `snet-intern` ist vorhanden
- Input «Netzwerksicherheitsgruppen (NSG)»
- Cloud Shell (Bash) und PowerShell auf dem Laptop, wie in Auftrag 3.3
- Dein öffentlicher Schlüssel (Public Key) aus Auftrag 1.6
- Lernjournal: Ordner `tag-4/4.3-zwei-vms-im-vnet`

## Ausgangslage
Die Velo Zürich AG stellt einen Webserver ins Subnetz (Subnet) `snet-web` und einen internen Server ins Subnetz (Subnet) `snet-intern`. Der Webserver bekommt eine öffentliche IP (Public IP), damit er aus dem Internet erreichbar ist. Der interne Server bekommt **keine**: Er soll nur im VNet erreichbar sein.

So sieht es am Schluss aus:
```text
   Internet (dein Laptop)
            │
        Public IP
            │
            ▼
┌─ vnet-tag4-<kuerzel> · 10.10.0.0/16 ────────────────────────┐
│  ┌─ snet-web ──────────┐        ┌─ snet-intern ─────────┐   │
│  │  10.10.1.0/24       │        │  10.10.2.0/24         │   │
│  │  nsg-web            │        │                       │   │
│  │  vm-web  10.10.1.4  │ ─────► │  vm-intern 10.10.2.4  │   │
│  └─────────────────────┘        └───────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

| Was | Wert (Beispiel für `mm`) |
|-----|--------------------------|
| NSG für `snet-web` | `nsg-web` |
| Webserver | `vm-web-mm` in `snet-web`, mit öffentlicher IP (Public IP) |
| interner Server | `vm-intern-mm` in `snet-intern`, ohne öffentliche IP (Public IP) |

> [!TIP]
> **So arbeitet ihr zu zweit:** Jede Person baut alles in ihrem eigenen Abonnement (Subscription). Ihr sitzt nebeneinander, macht jeden Schritt gleichzeitig und vergleicht nach jeder **Kontrolle**. Wer schneller ist, hilft.

> [!IMPORTANT]
> Heute laufen bei dir **zwei** VMs gleichzeitig. Prüfe zuerst, dass keine VM von Tag 3 mehr läuft:
> ```bash
> az vm list --output table
> ```
> Die Ausgabe muss leer sein. Sonst lösche zuerst die alte Ressourcengruppe (Resource Group).

## Auftrag

### Schritt 1: Öffentlichen Schlüssel in der Cloud Shell speichern
Die Cloud Shell hat die Variable `KEY` von Tag 3 vergessen. Speichere deinen öffentlichen Schlüssel (Public Key) neu, wie in Auftrag 3.3:
1. **PowerShell:** Zeige deinen öffentlichen Schlüssel (Public Key) an und kopiere die ganze Zeile:
   ```powershell
   Get-Content ~\.ssh\id_ed25519.pub
   ```
2. **Cloud Shell:** Tippe `KEY="`, füge die kopierte Zeile ein (`Ctrl` + `Shift` + `V`), tippe `"` und drücke `Enter`.
3. **Cloud Shell:** Prüfe, was in der Variablen steht:
   ```bash
   echo $KEY
   ```

**Kontrolle:** Die Ausgabe ist eine lange Zeile, die mit `ssh-ed25519 AAAA` beginnt.

### Schritt 2: NSG erstellen
Eine NSG ist eine Liste von Sicherheitsregeln (Security Rules). Du erstellst sie zuerst leer und fügst dann eine Sicherheitsregel (Security Rule) für SSH hinzu.
```bash
az network nsg create --resource-group rg-tag4-<kuerzel> --name nsg-web
az network nsg rule create --resource-group rg-tag4-<kuerzel> --nsg-name nsg-web --name allow-ssh --priority 1000 --direction Inbound --access Allow --protocol Tcp --destination-port-ranges 22 --source-address-prefixes '*'
```

| Option | Bedeutung |
|--------|-----------|
| `--priority 1000` | Priorität (Priority): Kleine Zahlen werden zuerst geprüft. |
| `--direction Inbound` | gilt für Verkehr, der **herein**kommt |
| `--access Allow` | erlauben |
| `--protocol Tcp --destination-port-ranges 22` | SSH |
| `--source-address-prefixes '*'` | Quelle (Source): von überall |

> [!WARNING]
> SSH von überall ist nur für den Moment. In Auftrag 4.4 schränkst du die Quelle (Source) auf die IP-Adresse der Schule ein.

**Kontrolle:** Die Ausgabe des zweiten Befehls enthält `"name": "allow-ssh"` und `"access": "Allow"`.

### Schritt 3: NSG mit dem Subnetz verknüpfen
```bash
az network vnet subnet update --resource-group rg-tag4-<kuerzel> --vnet-name vnet-tag4-<kuerzel> --name snet-web --network-security-group nsg-web
```
Ab jetzt gelten die Sicherheitsregeln (Security Rules) von `nsg-web` für **jede** VM im Subnetz (Subnet) `snet-web`.

**Kontrolle:** In der Ausgabe steht bei `"networkSecurityGroup"` eine ID, die mit `nsg-web` endet.

### Schritt 4: Webserver-VM erstellen
```bash
az vm create --resource-group rg-tag4-<kuerzel> --name vm-web-<kuerzel> --image Ubuntu2404 --size Standard_B1s --admin-username azureuser --ssh-key-values "$KEY" --vnet-name vnet-tag4-<kuerzel> --subnet snet-web --public-ip-sku Standard --nsg ""
```
Den Befehl kennst du aus Auftrag 3.3. Neu sind drei Optionen:

| Option | Bedeutung |
|--------|-----------|
| `--vnet-name vnet-tag4-<kuerzel>` | in dein VNet statt in ein neues |
| `--subnet snet-web` | in dieses Subnetz (Subnet) |
| `--nsg ""` | **keine** eigene NSG an der Netzwerkschnittstelle (Network Interface). Es gilt nur `nsg-web` am Subnetz (Subnet). |

<!-- prüfen: Stand 10.11.2026 – zwei VMs Standard_B1s gleichzeitig im vCPU-Kontingent des Student-Abos -->

**Kontrolle:** In der Ausgabe stehen `"powerState": "VM running"`, `"privateIpAddress": "10.10.1.4"` und bei `"publicIpAddress"` eine Adresse. Notiere die öffentliche IP (Public IP).

### Schritt 5: Interne VM erstellen
```bash
az vm create --resource-group rg-tag4-<kuerzel> --name vm-intern-<kuerzel> --image Ubuntu2404 --size Standard_B1s --admin-username azureuser --ssh-key-values "$KEY" --vnet-name vnet-tag4-<kuerzel> --subnet snet-intern --public-ip-address "" --nsg ""
```
`--public-ip-address ""` heisst: **keine** öffentliche IP (Public IP).

**Kontrolle:** In der Ausgabe stehen `"privateIpAddress": "10.10.2.4"` und `"publicIpAddress": ""`.

### Schritt 6: Alle Adressen auf einen Blick
```bash
az vm list-ip-addresses --resource-group rg-tag4-<kuerzel> --output table
```

**Kontrolle:**
```text
VirtualMachine       PublicIPAddresses    PrivateIPAddresses
-------------------  -------------------  --------------------
vm-intern-<kuerzel>                       10.10.2.4
vm-web-<kuerzel>     20.…                 10.10.1.4
```

### Schritt 7: Am Webserver anmelden (PowerShell)
```powershell
ssh azureuser@<öffentliche-ip>
```
Tippe beim ersten Verbinden `yes`. Zeige dann in der VM die private IP-Adresse an:
```bash
hostname -I
```
`hostname -I` zeigt die IP-Adressen der VM. Die öffentliche IP (Public IP) siehst du hier nicht: Sie liegt bei Azure, nicht in der VM.

**Kontrolle:** Die Ausgabe ist `10.10.1.4`.

### Schritt 8: Den internen Server anpingen (in vm-web)
`ping` schickt kleine Testpakete an eine Adresse und wartet auf Antwort. `-c 4` heisst: vier Pakete.
```bash
ping -c 4 10.10.2.4
```

**Kontrolle:** Die letzte Zeile enthält `4 received, 0% packet loss`. Die zwei VMs in verschiedenen Subnetzen (Subnets) erreichen sich.

Beende die Verbindung mit `exit`.

### Schritt 9: Über den Webserver auf den internen Server (PowerShell)
`vm-intern` hat keine öffentliche IP (Public IP). Du erreichst ihn trotzdem: über `vm-web` als **Sprungserver** (Jump Host). Die Option `-J` sagt SSH, dass es zuerst zu `vm-web` und von dort weiter springen soll. Dein Schlüssel bleibt dabei auf dem Laptop.
```powershell
ssh -J azureuser@<öffentliche-ip> azureuser@10.10.2.4
```
Tippe bei der Frage nach dem neuen Server `yes`.

**Kontrolle:** Die Eingabezeile ist `azureuser@vm-intern-<kuerzel>:~$`.

### Schritt 10: Zurück pingen (in vm-intern)
```bash
ping -c 4 10.10.1.4
exit
```

**Kontrolle:** Wieder `0% packet loss`. Nach `exit` bist du zurück in der PowerShell.

### Schritt 11: Fragen
Beantworte im Lernjournal.

1. Ordne zu: Welche Adresse gehört wohin?

   | Adresse | vm-web | vm-intern | Subnetz (Subnet) snet-web | Subnetz (Subnet) snet-intern |
   |---------|:------:|:---------:|:-------------------------:|:----------------------------:|
   | `10.10.1.4` | | | | |
   | `10.10.2.4` | | | | |

   Kreuze pro Zeile eine VM und ein Subnetz (Subnet) an.
2. Kreuze an: Warum kannst du dich nicht direkt vom Laptop mit `ssh azureuser@10.10.2.4` an `vm-intern` anmelden?
   - [ ] Die NSG blockiert Port 22.
   - [ ] `10.10.2.4` ist eine private Adresse. Sie ist nur im VNet erreichbar.
   - [ ] `vm-intern` hat kein SSH installiert.
3. In `nsg-web` gibt es nur die Sicherheitsregel (Security Rule) `allow-ssh` für Port 22. Trotzdem kommt der Ping von `vm-intern` bei `vm-web` an. Welche Standardsicherheitsregel (Default Security Rule) lässt ihn durch? Schau in [Kapitel 6](../../theorie/06-azure-networking.md) nach.
   - [ ] `AllowVnetInBound`
   - [ ] `AllowInternetOutBound`
   - [ ] `DenyAllInBound`

## Wenn etwas nicht klappt

| Problem | Lösung |
|---------|--------|
| `QuotaExceeded` oder Fehler mit `cores` | Es läuft noch eine VM von Tag 3. `az vm list --output table`, alte Ressourcengruppe (Resource Group) löschen. |
| `SkuNotAvailable` | `Standard_B1s` durch `Standard_B2ats_v2` ersetzen. |
| `privateIpAddress` ist `10.0.0.4` | `--vnet-name` oder `--subnet` vergessen: Azure hat ein neues VNet erstellt. VM löschen (`az vm delete --resource-group rg-tag4-<kuerzel> --name <vm-name> --yes`) und Schritt neu machen. |
| `ssh` in Schritt 7 hängt und bricht mit `Connection timed out` ab | Schritt 3 prüfen: Ist `nsg-web` mit `snet-web` verknüpft? Ohne NSG lässt die öffentliche IP (Public IP) gar nichts herein. |
| `ssh -J` meldet `Permission denied (publickey)` | Benutzer `azureuser` bei **beiden** Adressen? Gleicher Schlüssel bei beiden VMs (Schritt 1)? |

> [!NOTE]
> **Lange Pause (z. B. Mittag)?** Freigeben spart Kosten. Danach wieder starten:
> ```bash
> az vm deallocate --resource-group rg-tag4-<kuerzel> --name vm-web-<kuerzel>
> az vm deallocate --resource-group rg-tag4-<kuerzel> --name vm-intern-<kuerzel>
> ```
> Nach der Pause: dieselben Befehle mit `az vm start` statt `az vm deallocate`.
