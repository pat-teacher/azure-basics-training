# Auftrag 5.2: Erste Bicep-Datei – ein Speicherkonto

Zeit: 45 Min. · Form: Einzelarbeit

## Ziel
- Du kannst eine Bicep-Datei lesen und mit der Azure CLI bereitstellen. (K3)
- Du kannst mit `what-if` vorhersagen, was eine Bereitstellung (Deployment) ändert. (K3)
- Du kannst an einem Beispiel zeigen, dass Bicep idempotent ist und zu einem ARM-Template wird. (K2)
- Du kannst den Unterschied zwischen `az deployment group` und `az deployment sub` erklären. (K2)

## Voraussetzungen
- Auftrag 5.1 erledigt, Ordner `azure-tag5` in Visual Studio Code geöffnet
- Bicep-Erweiterung aus Auftrag 4.8
- Theorie zum Nachlesen: [Kapitel 7 Automatisierung](../../theorie/07-automatisierung.md), Abschnitt «ARM-Templates und Bicep»
- Lernjournal: Ordner `tag-5/5.2-erste-bicep-datei`

## Ausgangslage
An Tag 3 hast du ein Speicherkonto (Storage Account) im Portal erstellt. Heute beschreibst du es in einer **Bicep-Datei**. Du schreibst nicht, **wie** Azure es erstellen soll. Du schreibst, **was** am Schluss da sein soll. Azure vergleicht das mit dem, was schon existiert, und macht nur, was fehlt.

Du stellst die Datei zuerst mit `az deployment group` bereit. Dafür erstellst du die Ressourcengruppe (Resource Group) vorher von Hand. Danach löschst du alles und stellst es nochmals bereit, diesmal mit `az deployment sub`. Dann erstellt Bicep auch die Ressourcengruppe (Resource Group).

## Auftrag

### Schritt 1: Bicep-Datei anlegen
1. Lege im Explorer von Visual Studio Code im Ordner `azure-tag5` einen Ordner `5.2` an (Rechtsklick > **New Folder**).
2. Lege darin die Datei `storage.bicep` an und kopiere diesen Inhalt hinein:
   ```bicep
   param location string = resourceGroup().location
   param kuerzel string

   resource st 'Microsoft.Storage/storageAccounts@2023-05-01' = {
     name: 'sttag5bicep${kuerzel}'
     location: location
     sku: { name: 'Standard_LRS' }
     kind: 'StorageV2'
   }

   output blobUrl string = st.properties.primaryEndpoints.blob
   ```
3. Speichere mit `Ctrl` + `S`.
4. Wechsle im Terminal in den Ordner:
   ```powershell
   cd $HOME\azure-tag5\5.2
   ```

| Zeile | Bedeutung |
|-------|-----------|
| `param kuerzel string` | Eingabewert. Du gibst ihn beim Bereitstellen mit. |
| `param location … = resourceGroup().location` | Eingabewert mit Standardwert: die Region der Ressourcengruppe (Resource Group) |
| `resource st '…storageAccounts@2023-05-01'` | Diese Ressource soll existieren. `st` ist der Name in der Datei, `2023-05-01` die API-Version. |
| `'sttag5bicep${kuerzel}'` | `${…}` setzt den Wert von `kuerzel` in den Text ein. |
| `output blobUrl` | Wert, den Azure nach der Bereitstellung (Deployment) ausgibt |

**Kontrolle:** Die Datei ist farbig hervorgehoben, und es gibt keine rote Wellenlinie. Fährst du mit der Maus über `storageAccounts`, zeigt die Bicep-Erweiterung eine Erklärung.

### Schritt 2: Ressourcengruppe von Hand erstellen
`az deployment group` stellt in eine Ressourcengruppe (Resource Group) bereit, die **schon existiert**. Darum erstellst du sie zuerst mit einem eigenen Befehl:
```powershell
az group create --name rg-tag5-<kuerzel> --location <region> --tags kurs=azure-basics tag=5 owner=<kuerzel>
```

**Kontrolle:** `"provisioningState": "Succeeded"`.

### Schritt 3: Vorschau mit what-if
`what-if` zeigt, was passieren **würde**, ohne etwas zu ändern.
```powershell
az deployment group what-if --resource-group rg-tag5-<kuerzel> --template-file storage.bicep --parameters kuerzel=<kuerzel>
```

**Kontrolle:** Die Ausgabe zeigt eine Zeile mit `+ Microsoft.Storage/storageAccounts/sttag5bicep<kuerzel>` und am Schluss `Resource changes: 1 to create.`

### Schritt 4: Bereitstellen
```powershell
az deployment group create --resource-group rg-tag5-<kuerzel> --template-file storage.bicep --parameters kuerzel=<kuerzel> --query properties.outputs
```
`--query properties.outputs` zeigt nur die Ausgabewerte statt des ganzen JSON.

**Kontrolle:** Die Ausgabe zeigt `blobUrl` mit dem Wert `https://sttag5bicep<kuerzel>.blob.core.windows.net/`.

### Schritt 5: Nochmals ausführen
Führe **genau denselben** Befehl wie in Schritt 4 nochmals aus. Ein Skript mit vielen einzelnen CLI-Befehlen müsstest du dafür so schreiben, dass es mit schon vorhandenen Ressourcen umgehen kann. Bicep macht das von selbst.

**Kontrolle:** Kein Fehler, dieselbe Ausgabe. Azure hat nichts geändert, weil der Zielzustand schon erreicht ist. Diese Eigenschaft heisst **Idempotenz**.

### Schritt 6: Etwas ändern
Die Velo Zürich AG will ihre Daten in zwei Regionen sichern (Input 5, Redundanz (Redundancy)). Ändere in `storage.bicep` die Zeile mit `sku` auf:
```bicep
  sku: { name: 'Standard_GRS' }
```
Speichere und schau dir zuerst die Vorschau an:
```powershell
az deployment group what-if --resource-group rg-tag5-<kuerzel> --template-file storage.bicep --parameters kuerzel=<kuerzel>
```

**Kontrolle:** Die Ausgabe zeigt `~ Microsoft.Storage/storageAccounts/…` und darunter `sku.name: "Standard_LRS" => "Standard_GRS"`. Am Schluss steht `1 to modify`.

Stelle jetzt bereit (Befehl aus Schritt 4) und prüfe:
```powershell
az storage account show --resource-group rg-tag5-<kuerzel> --name sttag5bicep<kuerzel> --query sku.name --output tsv
```

**Kontrolle:** Die Ausgabe ist `Standard_GRS`.

### Schritt 7: Das ARM-Template dahinter
Azure versteht Bicep nicht direkt. Die Azure CLI übersetzt die Datei vorher in ein **ARM-Template** (JSON).
```powershell
az bicep build --file storage.bicep
(Get-Content storage.bicep).Count
(Get-Content storage.json).Count
```
`az bicep build` schreibt die Übersetzung in `storage.json`. `(Get-Content …).Count` zählt die Zeilen einer Datei.

**Kontrolle:** Im Explorer erscheint `storage.json`. Sie hat ein Vielfaches an Zeilen. Öffne sie und such die Zeile `"type": "Microsoft.Storage/storageAccounts"`.

### Schritt 8: Alles löschen
Du hast zwei Befehle gebraucht: `az group create` und `az deployment group create`. Jetzt löschst du alles und baust es danach mit **einem** Befehl neu.
```powershell
az group delete --name rg-tag5-<kuerzel> --yes
```
Ohne `--no-wait` wartet der Befehl, bis alles gelöscht ist. Das dauert 1–3 Minuten.

```powershell
az group exists --name rg-tag5-<kuerzel>
```
`az group exists` prüft, ob es die Ressourcengruppe (Resource Group) gibt.

**Kontrolle:** Die Ausgabe ist `false`.

### Schritt 9: Die Ressourcengruppe gehört auch in Bicep
Lege im Ordner `5.2` eine zweite Datei `main.bicep` an und kopiere diesen Inhalt hinein:
```bicep
targetScope = 'subscription'

param location string = deployment().location
param kuerzel string

resource rg 'Microsoft.Resources/resourceGroups@2022-09-01' = {
  name: 'rg-tag5-${kuerzel}'
  location: location
  tags: {
    kurs: 'azure-basics'
    tag: '5'
    owner: kuerzel
  }
}

module storage 'storage.bicep' = {
  name: 'storage-${kuerzel}'
  scope: rg
  params: {
    location: location
    kuerzel: kuerzel
  }
}

output blobUrl string = storage.outputs.blobUrl
```
`storage.bicep` bleibt, wie sie ist.

| Zeile | Bedeutung |
|-------|-----------|
| `targetScope = 'subscription'` | Diese Datei wird im Abonnement (Subscription) bereitgestellt, nicht in einer Ressourcengruppe (Resource Group). Nur so kann sie eine Ressourcengruppe (Resource Group) erstellen. |
| `deployment().location` | die Region, die du beim Bereitstellen mit `--location` angibst |
| `resource rg '…resourceGroups…'` | Die Ressourcengruppe (Resource Group) ist jetzt eine Ressource in der Datei, mit Tags. |
| `module storage 'storage.bicep'` | ruft deine Datei aus Schritt 1 auf |
| `scope: rg` | `storage.bicep` wird in die Ressourcengruppe (Resource Group) `rg` bereitgestellt. Bicep erstellt darum zuerst `rg`. |
| `params: { … }` | die Werte für die `param`-Zeilen in `storage.bicep` |
| `storage.outputs.blobUrl` | gibt den `output` von `storage.bicep` weiter |

**Kontrolle:** Keine rote Wellenlinie in `main.bicep`.

### Schritt 10: Mit einem Befehl bereitstellen
Statt `--resource-group` gibst du jetzt `--location` an. Ersetze `<region>` durch deine Kursregion, z. B. `switzerlandnorth`.
```powershell
az deployment sub what-if --location <region> --template-file main.bicep --parameters kuerzel=<kuerzel>
```

**Kontrolle:** Zwei Zeilen mit `+`: `Microsoft.Resources/resourceGroups/rg-tag5-<kuerzel>` und `Microsoft.Storage/storageAccounts/sttag5bicep<kuerzel>`. <!-- prüfen: what-if-Ausgabe auf Ebene Abonnement mit Ressourcengruppe und Speicherkonto -->

```powershell
az deployment sub create --location <region> --template-file main.bicep --parameters kuerzel=<kuerzel> --query properties.outputs
```

**Kontrolle:** Die Ausgabe zeigt wieder `blobUrl`. Prüfe die Tags:
```powershell
az group show --name rg-tag5-<kuerzel> --query tags
```
Die Ausgabe zeigt `kurs`, `owner` und `tag`. Kein `az group create` nötig.

So unterscheiden sich die beiden Befehle:

| | `az deployment group create` | `az deployment sub create` |
|---|---|---|
| Wo wird bereitgestellt? | in einer Ressourcengruppe (Resource Group) | im Abonnement (Subscription) |
| Ressourcengruppe (Resource Group) | vorher von Hand mit `az group create` | steht in `main.bicep` |
| Angabe im Befehl | `--resource-group rg-…` | `--location <region>` |
| Erste Zeile der Datei | – | `targetScope = 'subscription'` |

Ab Auftrag 5.3 stellst du immer mit `az deployment sub` bereit.

### Schritt 11: Fragen
Beantworte im Lernjournal.
1. Ordne die Zeichen aus der what-if-Ausgabe zu: `+`, `~`, `-`, `=`

   | Zeichen | Bedeutung |
   |---------|-----------|
   | | wird geändert |
   | | wird erstellt |
   | | bleibt gleich |
   | | wird gelöscht |

2. Kreuze an: Was bedeutet «Idempotenz»?
    - [ ] Die Datei läuft nur einmal.
    - [ ] Mehrmals ausführen ergibt dasselbe Ergebnis wie einmal ausführen.
    - [ ] Azure löscht vor jeder Bereitstellung (Deployment) alles.
3. Wie viele Zeilen hatten `storage.bicep` und `storage.json`? Warum schreibt man lieber Bicep? Antworte in einem Satz.
4. Kreuze an: Warum brauchst du mit `az deployment sub` kein `az group create`?
    - [ ] Azure erstellt bei jeder Bereitstellung (Deployment) automatisch eine Ressourcengruppe (Resource Group).
    - [ ] Die Ressourcengruppe (Resource Group) steht als Ressource in `main.bicep`.
    - [ ] Mit `az deployment sub` braucht es keine Ressourcengruppe (Resource Group).

## Wenn etwas nicht klappt

| Problem | Lösung |
|---------|--------|
| `StorageAccountAlreadyTaken` | Name schon vergeben. In `storage.bicep` zwei Ziffern anhängen, z. B. `'sttag5bicep${kuerzel}07'`. |
| `AccountNameInvalid` | Kürzel mit Grossbuchstaben oder Bindestrich. Nur Kleinbuchstaben und Ziffern. |
| `The system cannot find the file …` | Falscher Ordner: `cd $HOME\azure-tag5\5.2` |
| rote Wellenlinie im Editor | Tippfehler. Fahr mit der Maus darüber, die Erweiterung erklärt den Fehler. |
| `az bicep build` meldet, Bicep fehle | `az bicep install` |
| `the following arguments are required: --location` | Bei `az deployment sub` fehlt `--location <region>`. |
| Fehler zu `targetScope` oder `scope` | Falscher Befehl für die Datei: `main.bicep` mit `az deployment sub`, `storage.bicep` mit `az deployment group`. |
| `InvalidDeploymentLocation` | Eine frühere Bereitstellung (Deployment) mit dem Namen `main` lief in einer anderen Region. Immer dieselbe Region bei `--location` angeben. <!-- prüfen: genauer Fehlertext --> |
| Schritt 10 erstellt die Ressourcengruppe (Resource Group) nicht neu | Schritt 8 war noch nicht fertig. Warten, bis `az group exists` `false` zeigt, dann Schritt 10 wiederholen. |

## Aufräumen
Machst du direkt mit Auftrag 5.3 weiter, kannst du die Ressourcengruppe (Resource Group) stehen lassen. 5.3 stellt das Netzwerk in dieselbe Ressourcengruppe (Resource Group) bereit.

Machst du jetzt eine längere Pause, lösche sie. 5.3 erstellt sie mit `az deployment sub` selbst wieder.
```powershell
az group delete --name rg-tag5-<kuerzel> --yes --no-wait
```
