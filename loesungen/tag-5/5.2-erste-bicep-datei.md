# Lösung 5.2: Erste Bicep-Datei – ein Speicherkonto

Beispiel mit Kürzel `mm` und Region `switzerlandnorth`.

## Schritt 3
```text
Resource and property changes are indicated with this symbol:
  + Create

The deployment will update the following scope:

Scope: /subscriptions/…/resourceGroups/rg-tag5-mm

  + Microsoft.Storage/storageAccounts/sttag5bicepmm [2023-05-01]
      …

Resource changes: 1 to create.
```

## Schritt 4 und 5
```powershell
az deployment group create --resource-group rg-tag5-mm --template-file storage.bicep --parameters kuerzel=mm --query properties.outputs
```
```json
{
  "blobUrl": {
    "type": "String",
    "value": "https://sttag5bicepmm.blob.core.windows.net/"
  }
}
```
Beim zweiten Ausführen: dieselbe Ausgabe, kein Fehler.

## Schritt 6
```text
  ~ Microsoft.Storage/storageAccounts/sttag5bicepmm [2023-05-01]
    ~ properties.accessTier: "Hot" => "Cool"

Resource changes: 1 to modify.
```
<!-- prüfen: what-if-Ausgabe accessTier -->
`az storage account show … --query accessTier --output tsv` → `Cool`.

## Schritt 7
`storage.bicep` hat 12 Zeilen, `storage.json` je nach Bicep-Version rund 50–60 Zeilen. <!-- prüfen: Zeilenzahl storage.json -->

## Schritt 8
```powershell
az group delete --name rg-tag5-mm --yes
az group exists --name rg-tag5-mm
```
```text
false
```

## Schritt 9 und 10
`main.bicep` wie im Auftrag. Bereitstellen:
```powershell
az deployment sub what-if --location switzerlandnorth --template-file main.bicep --parameters kuerzel=mm
az deployment sub create --location switzerlandnorth --template-file main.bicep --parameters kuerzel=mm --query properties.outputs
az group show --name rg-tag5-mm --query tags
```
what-if (gekürzt): <!-- prüfen: Darstellung der Ausgabe auf Ebene Abonnement -->
```text
Scope: /subscriptions/…

  + Microsoft.Resources/resourceGroups/rg-tag5-mm [2022-09-01]

Scope: /subscriptions/…/resourceGroups/rg-tag5-mm

  + Microsoft.Storage/storageAccounts/sttag5bicepmm [2023-05-01]

Resource changes: 2 to create.
```
Die Ausgabe von `create` zeigt dieselbe `blobUrl` wie in Schritt 4. Das Speicherkonto (Storage Account) hat wieder die Zugriffsebene (Access Tier) `Cool`, weil `storage.bicep` seit Schritt 6 so lautet.
```json
{
  "kurs": "azure-basics",
  "owner": "mm",
  "tag": "5"
}
```

## Schritt 11
1. `+` wird erstellt, `~` wird geändert, `=` bleibt gleich, `-` wird gelöscht.
2. Mehrmals ausführen ergibt dasselbe Ergebnis wie einmal ausführen.
3. Zum Beispiel: «12 gegen 55 Zeilen. Bicep ist kürzer und lesbarer, das ARM-Template erzeugt Azure daraus selbst.»
4. Die Ressourcengruppe (Resource Group) steht als Ressource in `main.bicep`.

## Typische Fehler

| Problem | Ursache | Lösung |
|---------|---------|--------|
| `StorageAccountAlreadyTaken` | Name global vergeben | Ziffern anhängen |
| `--parameters` vergessen | `kuerzel` hat keinen Standardwert | Azure fragt interaktiv nach oder meldet einen Fehler; Parameter angeben |
| what-if zeigt `- Delete` | `--mode Complete` verwendet | ohne `--mode` arbeiten (Standard ist Incremental) |
| what-if zeigt `+ Create` statt `~ Modify` | Name des Speicherkontos (Storage Account) geändert | Name zurücksetzen; ein neuer Name erstellt ein zweites Speicherkonto (Storage Account) |
| `main.bicep` mit `az deployment group` bereitgestellt | Datei hat `targetScope = 'subscription'` | `az deployment sub create --location …` |
| `storage.bicep` mit `az deployment sub` bereitgestellt | `resourceGroup()` gibt es auf Ebene Abonnement (Subscription) nicht | immer `main.bicep` angeben |
| `--location` fehlt bei `az deployment sub` | Pflichtangabe: Dort speichert Azure die Angaben zur Bereitstellung (Deployment) | `--location <region>` ergänzen |
| `InvalidDeploymentLocation` | Bereitstellung (Deployment) `main` existiert schon mit anderer Region | dieselbe Region verwenden oder `--name main2` angeben |
| Schritt 10 meldet, dass die Ressourcengruppe (Resource Group) gelöscht wird | Schritt 8 mit `--no-wait` ausgeführt und nicht gewartet | warten, bis `az group exists` `false` zeigt |

## Hinweise für die Kursleitung
- Schritt 5 ist der Kern zur Idempotenz: Viele erwarten beim zweiten `create` einen Fehler. Kurz in der Klasse fragen, wer das vorhergesagt hätte.
- Schritte 8–10 zeigen den Unterschied `group` gegenüber `sub`: zuerst zwei Befehle (Ressourcengruppe (Resource Group) von Hand, dann Bereitstellung (Deployment)), danach einer. Ab 5.3 und im Abschlussprojekt stellen die Lernenden nur noch mit `az deployment sub` bereit.
- Schritt 6 ändert bewusst die Zugriffsebene (Access Tier) und nicht die Redundanz (Redundancy): `Standard_GRS` scheitert in Regionen ohne Regionspaar (Region Pair), und LRS → ZRS ist eine Konvertierung, die Stunden dauern kann.
- `module` nur als «ruft die andere Datei auf» erklären. Wer fragt: Ein Bicep-Modul (Bicep Module) ist eine Bicep-Datei, die eine andere aufruft, hier mit einem anderen Bereich (Scope).
- Der Name der Bereitstellung (Deployment) auf Ebene Abonnement (Subscription) ist ohne `--name` der Dateiname, also `main`. Er gilt im ganzen Abonnement (Subscription). Darum melden 5.3 und das Abschlussprojekt `InvalidDeploymentLocation`, wenn jemand die Region wechselt.
- Die Ressourcengruppe (Resource Group) `rg-tag5-<kuerzel>` bleibt für 5.3 stehen. Kosten: Rappenbeträge. Ist sie gelöscht, erstellt 5.3 sie neu.
- Zeit: Schritt 8 braucht 1–3 Minuten Wartezeit. Wer knapp ist, lässt Schritt 7 aus und holt ihn nach.
