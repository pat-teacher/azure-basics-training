# Lösung 4.3: Zwei VMs im VNet, Verbindungen testen

Beispiel mit Kürzel `mm`.

## Schritt 1
```bash
KEY="ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI… mia@LAPTOP-123"
```

## Schritt 2
```bash
az network nsg create --resource-group rg-tag4-mm --name nsg-web
az network nsg rule create --resource-group rg-tag4-mm --nsg-name nsg-web --name allow-ssh --priority 1000 --direction Inbound --access Allow --protocol Tcp --destination-port-ranges 22 --source-address-prefixes '*'
```

## Schritt 3
```bash
az network vnet subnet update --resource-group rg-tag4-mm --vnet-name vnet-tag4-mm --name snet-web --network-security-group nsg-web
```

## Schritt 4
```bash
az vm create --resource-group rg-tag4-mm --name vm-web-mm --image Ubuntu2404 --size Standard_B1s --admin-username azureuser --ssh-key-values "$KEY" --vnet-name vnet-tag4-mm --subnet snet-web --public-ip-sku Standard --nsg ""
```
```json
{
  "powerState": "VM running",
  "privateIpAddress": "10.10.1.4",
  "publicIpAddress": "20.208.51.90",
  …
}
```

## Schritt 5
```bash
az vm create --resource-group rg-tag4-mm --name vm-intern-mm --image Ubuntu2404 --size Standard_B1s --admin-username azureuser --ssh-key-values "$KEY" --vnet-name vnet-tag4-mm --subnet snet-intern --public-ip-address "" --nsg ""
```
```json

  "privateIpAddress": "10.10.2.4",
```

## Schritt 11
1. `10.10.1.4` → vm-web, snet-web. `10.10.2.4` → vm-intern, snet-intern.
2. `10.10.2.4` ist eine private Adresse. Sie ist nur im VNet erreichbar.
3. `AllowVnetInBound`: Verkehr innerhalb des VNets ist standardmässig erlaubt, auch ICMP (Ping).

## Typische Fehler

| Problem | Ursache | Lösung |
|---------|---------|--------|
| `privateIpAddress` `10.0.0.4` | `--vnet-name`/`--subnet` vergessen, neues VNet `vm-web-mmVNET` entstanden | VM löschen, mit Optionen neu. Zusätzliches VNet stört nicht, wird mit der Ressourcengruppe (Resource Group) gelöscht. |
| VM bekommt eigene NSG `vm-web-mmNSG` | `--nsg ""` vergessen | geht trotzdem (SSH ist dort offen), aber in 4.4 wirken dann zwei NSGs. `az network nic update --resource-group rg-tag4-mm --name vm-web-mmVMNic --remove networkSecurityGroup` |
| SSH-Timeout auf `vm-web` | `nsg-web` nicht am Subnetz (Subnet); die öffentliche IP (Public IP) (Standard) lässt ohne NSG nichts herein | Schritt 3 wiederholen |
| `QuotaExceeded` | VM von Tag 3 läuft noch | alte Ressourcengruppe (Resource Group) löschen |
| `ssh -J` meldet `Permission denied (publickey)` | anderer Schlüssel bei einer der VMs oder Benutzer nicht `azureuser` | Benutzer prüfen; sonst VM mit richtigem `KEY` neu erstellen |
| `ssh -J` wird nicht unterstützt (alte OpenSSH-Version) | Windows-OpenSSH zu alt | Ausweichlösung: `ssh -o ProxyCommand="ssh -W %h:%p azureuser@<öffentliche-ip>" azureuser@10.10.2.4` |

## Hinweise für die Kursleitung
- Tandem: Jede Person baut im eigenen Abonnement (Subscription), damit in 4.5 beide eine eigene Umgebung zum «Stören» haben.
- Kosten: zwei `Standard_B1s` und eine öffentliche IP (Public IP) für einige Stunden, Rappenbeträge. Vor dem Mittag an `az vm deallocate` erinnern.
- `ssh -J` (Sprungserver (Jump Host)) ist neu und wirkt für viele wie Zauberei. Kurz an der Wandtafel zeigen: Laptop → vm-web → vm-intern. Azure Bastion wäre die verwaltete Lösung dafür, kostet aber mehr: nur erwähnen.
- Schritt 11, Frage 3 bereitet die Standardsicherheitsregeln (Default Security Rules) aus dem Input auf: Viele erwarten, dass «nur SSH erlaubt» auch Ping blockiert.
- Vorab mit dem eigenen Konto testen: zwei VMs gleichzeitig im vCPU-Kontingent, `--nsg ""` und `--public-ip-address ""` in der Cloud Shell. <!-- prüfen -->
