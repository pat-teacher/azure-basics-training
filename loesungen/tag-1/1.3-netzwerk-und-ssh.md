# Lösung 1.3: Netzwerk und SSH

Stand: 19.10.2026

## Teil A
- IP bei NAT: `10.0.2.15/24`, Gateway `10.0.2.2`.
- Die Portweiterleitung leitet `127.0.0.1:2222` auf Windows an Port `22` der VM weiter.
- `ssh -p 2222 <benutzer>@127.0.0.1` fragt beim ersten Mal nach dem Fingerabdruck und danach nach dem Passwort.

## Teil B
- Schlüssel liegen unter `C:\Users\<name>\.ssh\id_ed25519` (privat) und `id_ed25519.pub` (öffentlich).
- Windows hat kein `ssh-copy-id`. Der Befehl mit `Get-Content | ssh …` erledigt dasselbe und setzt gleich die nötigen Rechte (700 für `~/.ssh`, 600 für `authorized_keys`).
- In der VM prüfen:
  ```bash
  cat ~/.ssh/authorized_keys          # eine Zeile, beginnt mit ssh-ed25519
  ls -ld ~/.ssh                       # drwx------ (700)
  ls -l ~/.ssh/authorized_keys        # -rw------- (600)
  ```

## Teil C
- Bei der Netzwerkbrücke bekommt die VM eine IP aus dem Schul- bzw. Heimnetz, z. B. `192.168.1.57`.
- Andere Laptops erreichen die VM direkt, **sofern das WLAN keine Client-Isolation hat**.

## Teil D

| Modus | IP-Bereich der VM | VM erreicht Internet? | Host erreicht VM? | Andere Laptops erreichen VM? |
|-------|-------------------|-----------------------|-------------------|------------------------------|
| NAT | 10.0.2.x (privat, nur für diese VM) | ja | nein | nein |
| NAT + Portweiterleitung | 10.0.2.x | ja | ja, über `127.0.0.1:<port>` | nein (Host-IP 127.0.0.1) |
| Netzwerkbrücke | IP aus dem physischen Netz | ja | ja | ja |

12. **NAT** ist sicherer: Die VM ist von aussen unsichtbar. Nur die Ports, die du bewusst weiterleitest, sind erreichbar, und auch nur vom eigenen Laptop. Bei einer Brücke steht die VM mit offenem SSH im fremden Netz.

Bezug zu Azure: Eine NSG funktioniert ähnlich wie diese bewusste Freigabe einzelner Ports (Tag 4).

## Zusatzaufgabe ⭐
Am besten in einer eigenen Datei unter `/etc/ssh/sshd_config.d/`:
```bash
echo "PasswordAuthentication no" | sudo tee /etc/ssh/sshd_config.d/01-nur-schluessel.conf
sudo systemctl restart ssh
sudo sshd -T | grep passwordauthentication    # erwartet: passwordauthentication no
```
Die Dateien in `sshd_config.d/` werden alphabetisch gelesen, und der **erste** Wert gilt. Ubuntu legt unter Umständen `50-cloud-init.conf` mit `PasswordAuthentication yes` an. Deshalb beginnt der Dateiname mit `01-`.

## Typische Fehler
| Problem | Ursache | Lösung |
|---------|---------|--------|
| `Connection refused` | OpenSSH-Server nicht installiert | `sudo apt install -y openssh-server` |
| `Connection refused` auf 2222 | Portweiterleitung falsch (Gast-Port nicht 22) | Regel prüfen |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | VM neu installiert oder Klon, gleicher Port | `ssh-keygen -R "[127.0.0.1]:2222"` |
| Passwort wird trotz Schlüssel verlangt | Schlüssel in falscher Datei oder Rechte zu offen | `chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys` |
| Partner erreicht VM nicht (Brücke) | Client-Isolation im WLAN | als Erkenntnis festhalten; mit Hotspot oder LAN testen |

- Mit Hyper-V: Der «Default Switch» verhält sich wie NAT, aber Windows erreicht die VM direkt über ihre 172.x-IP. Ein «externer Switch» entspricht der Brücke.
